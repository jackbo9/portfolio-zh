# 人员身份与去重口径审计

## 结论

未来数据应按以下优先级识别人，而不是只按姓名或组织：

1. **账号系统的稳定 `userId`**：唯一主键；人员转组、改名或换邮箱时不换主键。
2. **登录邮箱**：标准化为小写后作为辅助匹配和异常校验；仅在稳定 `userId` 缺失时临时兜底。
3. **姓名 + 当月组织**：只用于 5 月历史回填和人工核验，不作为长期去重键。组织是随时间变化的属性，不应成为人的身份。

用户提出的“按登录邮箱去重”方向基本正确，但如果账号系统能提供稳定 `userId`，应把邮箱放在第二优先级。看板已经证明姓名可能重复或错配，而邮箱和真实账号 UUID 在 6、7 月的活跃记录中没有月内重复。

## 5 月与未来数据的处理决定

- **6 月起及未来：** 建立账号维表 `account_user_id → login_email / display_name / department / group`，组织字段按生效月份保存；费用事实表只按稳定 `account_user_id` 聚合。邮箱用于检查“一邮箱多 ID / 一 ID 多邮箱”，不直接决定归属。
- **零使用人员：** 从账号系统全量名单取得稳定 `account_user_id`，再与当月费用左连接。不要继续为零使用人员生成 `roster:` 身份。
- **5 月：** 保留为“历史汇总月”，不纳入个人额度分位数的主样本。若必须回填个人趋势，先用现有账号名单做一次人工 crosswalk：邮箱可查时优先邮箱；否则用标准化姓名加 5 月组织辅助判断；出现同名、转组或名称不一致时保持未匹配，不强行合并。
- **当前制度测算：** 个人基线优先使用 6、7 月；5 月只用于验证总费用量级和识别异常。上面两组重复在拿到原始 5 月记录或账号映射前，不改写原看板，只在分析中扣除一个“高置信重复”并展示含/不含第二组的敏感区间。

## 可直接采用的数据验收规则

- 真实 `account_user_id` 月内唯一且非空；同一 ID 的邮箱变化触发提示但不拆人。
- 登录邮箱月内应唯一；重复或为空进入异常清单。
- 姓名、部门、小组只作展示和当月归属，不参与费用去重。
- `may:`、`roster:` 等合成 ID 不进入跨月个人画像。
- 无法确定身份的历史行保留为“未匹配”，不得为凑齐趋势强制归并。
